# Design decisions

## Goal and non-goals

Replace the per-module download/instantiation of null-context with a provider, keeping every ID and tag byte-identical.
Non-goals: changing naming rules, removing the `context` variable, adding new label features (do that in later, separately versioned releases).

## Decisions

| # | Decision | Why | Alternatives |
|---|---|---|---|
| 1 | Pure-Go core (`internal/label`) with no Terraform types | Testable against vectors; reusable by data source and function | Logic inside provider code |
| 2 | Golden vectors generated by the real module | The module is the spec; no hand-written expectations | Hand-written tests |
| 3 | Data source **and** function share the core | Data source works on any Terraform with provider support; function avoids deferred reads (needs TF >= 1.8) | Function only |
| 4 | Data source type name equals the provider name: `data "null-context" "x" {}` | Matches the requested shape | `context_label` |
| 5 | Optional+Computed attributes share names with module outputs | Drop-in rename of `module.context.X` to `data.null-context.this.X`; Terraform 1.17 accepts normalized values differing from config (verified) | Separate output names / nested `result` |
| 6 | Explicit `context` **replaces** provider defaults | Simple, predictable; avoids merging two sources with first-set-wins fields | Layer defaults under context |
| 7 | `context` is a dynamic attribute | Accepts `self`/`normalized_context` objects of any shape, including the old module's | Typed object |
| 8 | `self` is the recommended chaining value | `normalized_context` loses `project`/`region` and keeps the parent's `Name` tag | - |
| 9 | **Baseline: Terraform >= 1.8.0, OpenTofu >= 1.7.0** for every module using the provider (decided 2026-11-23) | 1.8 is the first release with provider-defined functions, so both entry points work everywhere with one rule; verified on 1.8.0 and 1.17.2. The data source alone would work on any protocol-6 version (>= 1.0) but a single baseline avoids per-module conditionals | Per-module minimums |
| 10 | **Public Terraform Registry**, address `registry.terraform.io/raringgroup/null-context` (decided 2026-11-23) | Zero-config `init` for every stack; needs a public repo, GPG-signed releases | Private registry / filesystem mirror |
| 11 | **Provider name: `null-context`** (decided 2026-11-23): source `raringgroup/null-context`, repo/binary `terraform-provider-null-context`, `data "null-context"`, `provider::null-context::label()` | Same name as the module it replaces, so the migration is a rename. Hyphen on purpose: an underscore (`null_context`) would make Terraform infer the provider `null` from the resource-type prefix | `context` |

## Provider configuration inheritance

Child modules inherit an un-aliased `provider "null-context"` from the root automatically, but each module should still declare it in
`required_providers`. Version constraints across all modules must be mutually compatible or `init` fails.

## Caveat that affects migration

The vendored `_context.tf` declares `variable "context"` with a **non-null default object**. A migrated file that passes
`context = var.context` would therefore always give the data source an explicit context, and provider defaults would never apply.
For root-level use the migrated variable should default to `null`:

```hcl
variable "context" { type = any  default = null }

data "null-context" "this" {
  enabled = var.enabled   namespace = var.namespace   # ... same pass-through as today
  context = var.context   # null at the root -> provider defaults apply
}
output "self" { value = data.null-context.this.self }
```

Then `module.context.id` becomes `data.null-context.this.id` (sed-able). Decide whether root stacks should use provider defaults or keep passing a context.

## Version and compatibility

- Baseline for all consumers: Terraform >= 1.8.0 / OpenTofu >= 1.7.0 (decision 9). The provider speaks protocol 6.
- The current module requires `>= 0.13.0`; migrating raises the floor, so each migrated module must set `required_version = ">= 1.8.0"`.
- OpenTofu uses its own registry (`registry.opentofu.org`); publishing there is a separate step and OpenTofu is not yet tested.
- A data source read is deferred to apply when its inputs are unknown, which can break `count`/`for_each` over its outputs. Use the function in such spots.

## Answers received (2026-11-23)

1. Minimum version: left to the maintainer -> Terraform 1.8.0 / OpenTofu 1.7.0 (decision 9).
2. `project` is in `label_order`; `region` is not -> the `normalized_context` quirk changes real IDs for any module that chains through it. See `docs/PARITY.md` (worked example). Migration rule: audit `normalized_context` usage first.
3. Registry: public Terraform Registry (decision 10) -> see `docs/RELEASE.md`.

## Still open

1. Should a later release fix the `normalized_context` quirks behind an opt-in flag? (Changes IDs; needs a plan check per stack.)
2. Do any modules actually chain through `normalized_context` today? (Audit with grep; decides whether the quirk is latent or live.)
3. Publish to the OpenTofu registry too?
4. Provider defaults at the root: change the vendored `variable "context"` default to `null`, or keep passing an explicit context? (See the caveat above.)

## Migration sketch (phase 5, not started)

0. Audit: `grep -rn normalized_context` across modules; list the ones that chain through it.
1. Keep the module as a thin shim that calls the provider; verify with `terraform plan` (zero diff) on real stacks (phase 4).
2. Replace the vendored `_context.tf` in leaf modules first, then upward.
3. Pin the provider in `required_providers` and in the Terragrunt-generated provider block (the `context.hcl` hierarchy).
4. Release with signed checksums (goreleaser) to the public registry (see `docs/RELEASE.md`).
